# 管理端（admin-web）

> 管理端的职责边界由任务书 §4 划定：**管理员只管账号，不参与课堂。**
> 开启/关闭课堂、监督学生、私密语音全部属于老师端；
> 即使 ADMIN 也不能通过普通业务 API 开关别人的课堂。

---

## 1. 页面与路由

| 路由 | 页面 | 职责 |
| --- | --- | --- |
| `/admin/login` | 登录 | 账号 + 密码（Argon2id 校验，见 [authentication.md](../auth/authentication.md)） |
| `/admin/dashboard` | 概览 | 各角色账号数量 + 常用入口（不承载业务操作） |
| `/admin/users` | 账号列表 | 搜索 / 筛选 / 分页；改显示名、启用停用、重置老师密码 |
| `/admin/users/new` | 创建账号 | 创建老师（需密码）或学生（无密码） |

入口独立于 student/teacher：三个 SPA 物理分离，只有 admin-web 会加载用户管理相关代码
（任务书 §5）。学生端与老师端的产物里不存在这些页面与接口调用。

## 2. 账号列表

### 2.1 数据来源与语义

```http
GET /api/v1/admin/users?role=&status=&q=&page=1&pageSize=50
→ { "users": [...], "total": 123, "page": 1, "pageSize": 50 }
```

- 排序固定为 `created_at DESC, id DESC`：**稳定排序**是分页正确性的前提，
  否则翻页时会出现重复项或漏项（前端不提供"任意列排序"，V1 不需要）。
- `q` 同时匹配账号与显示名；账号是 citext，因此搜索天然大小写不敏感。
- `pageSize` 默认 50、上限 200：列表是给人看的，不是导出通道。
- 筛选条件与 `page` **同步到 URL query**：刷新、分享链接、浏览器前进后退都能保持视图；
  非法值（例如 `page=abc`）不会写回 URL，也不会发给后端。

### 2.2 列表里显示什么

| 列 | 说明 |
| --- | --- |
| 账号 | 学生账号是他们的登录凭据，管理员需要能读出来告知学生 |
| 显示名 | 中文姓名；可编辑 |
| 角色 | `ADMIN` / `TEACHER` / `STUDENT` 徽章 |
| 状态 | `ACTIVE` / `DISABLED` 徽章（绿 / 灰） |
| 创建时间 | 账号何时建立 |
| 上次登录 | `lastLoginAt`；从未登录显示 `never`——这是"账号发出去了但没人用过"的唯一线索 |

**绝不显示**密码、密码 hash、会话信息。接口本身也不返回这些字段。

### 2.3 行内操作

| 操作 | 可用条件 | 行为 |
| --- | --- | --- |
| 编辑显示名 | 任何账号 | `PATCH /users/:id`，只改 `displayName` |
| 启用 / 停用 | 除自己以外的账号 | `PATCH /users/:id/status`，二次确认 |
| 重置密码 | 仅 `TEACHER` 行 | `POST /admin/teachers/:id/reset-password` |

## 3. 创建账号

### 3.1 为什么没有"创建管理员"选项

任务书 §4 只赋予管理员"创建老师/学生"的能力，并且明确：
**第一个管理员由环境变量或初始化命令创建**（本项目是 `make create-admin`）。

- 管理端 API 一旦能创建 ADMIN，就等于给自己开了一条提权路径；
  一个被盗的管理员会话可以直接造出第二个管理员账号，问题从"会话泄漏"升级为"永久后门"。
- 因此 `POST /api/v1/admin/users` 对 `role: "ADMIN"` **直接拒绝**（400），
  界面上也不提供该选项，并写明原因——避免管理员以为是系统坏了。
- 需要第二个管理员时，由运维在服务器上执行：

  ```bash
  make create-admin      # 交互式，密码不回显、不进 shell 历史
  ```

### 3.2 为什么学生没有密码框

学生账号**没有密码**是任务书 §2.2 明确的业务模型（不是未完成的功能）：
学生只需输入账号即可进入课堂。因此：

- 表单在选择"学生"时**不渲染密码输入框**，并显示一行说明；
- 若通过其它方式提交了 `password`，后端会拒绝（400），数据库也有 `users_password_by_role`
  约束兜底——"带密码的学生"在这套系统里无法被创建出来。

### 3.3 老师密码

老师必须有密码，且至少 12 位（`PASSWORD_MIN_LENGTH`）。
密码策略由服务端校验，前端只做即时提示；`PASSWORD_POLICY_VIOLATION` 会被**挂到密码字段**上，
而不是弹一个笼统的顶部错误。

## 4. 编辑显示名：为什么不能改角色

`PATCH /api/v1/admin/users/:id` **只接受 `displayName`**：

- 任务书 §4 的管理员能力清单里没有"修改角色"；
- 改角色会牵动一堆语义：已有会话的角色、课堂归属（`classrooms.owner_teacher_id` 要求
  owner 必须是 TEACHER）、历史 Run 的归属。这些在 V1 都没有定义，贸然开放会制造
  数据一致性问题（例如把老师降级成学生后，他名下的课堂就没有合法所有者了）；
- 因此请求体里出现 `role` / `status` / `password` 等字段时，后端**返回 400 而不是静默忽略**——
  静默忽略会让前端以为修改成功了，是最难排查的一类 Bug。

需要"停用某个老师"时，用状态接口；需要"把学生变成老师"时，在 V1 里是**新建一个老师账号**。

## 5. 启用 / 停用

```http
PATCH /api/v1/admin/users/:id/status   { "status": "DISABLED" }
```

| 规则 | 原因 |
| --- | --- |
| 停用**立即撤销该账号全部会话** | 课堂正在进行时也必须立刻断开：被停用的账号不应该还能继续看课堂内容。前端文案直接说明这一点 |
| 启用**不恢复**旧会话 | 会话是"某次登录"，不是账号属性；重新启用后本人需要重新登录 |
| 设为当前值 → 幂等成功 | 两个管理员同时操作不应产生错误提示 |
| **禁止停用自己** → `409 CANNOT_DISABLE_SELF` | 防止管理员把自己锁在门外；前端也会禁用该行的停用按钮（后端仍然独立校验） |
| **禁止停用最后一个 ACTIVE 管理员** → `409 LAST_ADMIN_PROTECTED` | 否则系统将失去所有管理能力，只能靠 `adminctl` 破窗恢复 |

这两条规则有**各自独立的错误码**，而不是笼统的 `INVALID_REQUEST`：
管理界面必须把"为什么被拒绝"讲清楚（"不能停用你正在使用的账号" vs "系统必须保留至少一个管理员"），
而 `INVALID_REQUEST` 同时覆盖账号格式、未知字段等一堆原因。契约规定客户端按 `code` 分支（§58），
所以需要用户理解的产品规则就应当有自己的码——而不是让前端去解析后端的中文/英文句子。

## 6. 重置老师密码

```http
POST /api/v1/admin/teachers/:id/reset-password
{ "password": "可选" }
→ { "user": {...}, "password": "仅在服务端生成时返回，且只返回这一次" }
```

两种模式：

1. **管理员指定**：适合老师当面报一个他想要的密码。会按同一套密码策略校验。
2. **服务端生成**（不传 `password`）：`crypto/rand` 24 字节 → base64url（≈144 bit）。
   界面用弹窗**只展示一次**，带复制按钮，并明确提示"关闭后不再显示"。

为什么提供生成模式：现实中"管理员随便想一个密码"往往就是 `123456` 或老师的生日。
让服务端生成一个高熵密码，把"弱密码"这条风险从流程里去掉。生成的密码：

- 只在这一次响应里出现，**不写日志**、不落库（库里只有 Argon2id hash）；
- 前端不写入 localStorage / sessionStorage，弹窗关闭即从内存与 DOM 中移除。

重置密码会**撤销该老师的全部会话**：密码变了，旧会话不应该继续有效。

> 只允许重置 `TEACHER`：任务书 §4 定义的就是"重置老师密码"。
> 管理员自己的密码走 `adminctl reset-password` 破窗通道（服务器上执行）。

## 7. 权限与安全（管理端视角）

- 所有 `/api/v1/admin/**` 端点都同时经过：**会话中间件 → 角色校验（ADMIN）→ CSRF 校验（写方法）**。
  学生或老师会话访问会得到 `403 ROLE_FORBIDDEN`，没有会话得到 `401 AUTH_REQUIRED`。
- 管理端 Cookie 与其它两个入口**名称不同**（`classwatch_session_admin`），
  在同一个浏览器里可以同时登录三个入口而互不影响。
- 前端路由守卫、按钮禁用、"没有管理员选项"全部只是 UX：
  真正的边界在服务端，用 curl 直接调用同样会被拒绝（`docs/auth/rbac.md` §6）。

错误码 → 界面行为：

| 错误码 | 界面行为 |
| --- | --- |
| `ACCOUNT_ALREADY_EXISTS` | 挂到"账号"字段：账号已存在 |
| `PASSWORD_POLICY_VIOLATION` | 挂到"密码"字段：说明具体策略 |
| `USER_NOT_FOUND` | 顶部提示 + 刷新列表（可能已被其他人删除/改过） |
| `CANNOT_DISABLE_SELF` | 停用确认框内提示"不能停用你当前登录的账号，请换一个管理员登录" |
| `LAST_ADMIN_PROTECTED` | 停用确认框内提示"系统必须保留至少一个管理员，请先创建另一个管理员" |
| `INVALID_REQUEST` | 顶部提示通用原因（参数不合法、不允许的字段等） |
| `ROLE_FORBIDDEN` / `AUTH_REQUIRED` | 提示无权限/需要重新登录（守卫会处理跳转） |
| `RATE_LIMITED` | 顶部提示稍后重试（遵守 `Retry-After`） |
| 未知错误 | 通用提示，**绝不把 500 的原始报文显示出来** |
